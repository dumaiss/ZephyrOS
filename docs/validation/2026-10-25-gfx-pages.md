# GFX pages (asynchronous batches, page flipping, the partial present)

## Result

Drawing is asynchronous now: the backend waits for the VDP's command
engine before it starts each command, not after, so a batch (or a
call outside one) returns with the engine still drawing and the CPU
runs while the VDP finishes.  Every CPU VRAM path waits for the
engine first - the upload, the text sink, the palette, a mode set, a
page switch and `gfx_close` - so it can never race a running
command, and `gfx_wait` waits for the last command (gfx-sdk.md
§9.2).  Page flipping joins it (gfx-sdk.md §15.1): `gfx_show_page`
waits for the engine and the next vertical blank and then writes
R#2's page bit, so the switch is atomic; `gfx_wait_vblank` waits for
the start of the next retrace (VR low, then high, in polling
assembly), so a frame loop runs once per frame and a partial present
copies a band from the hidden page across the blank.  `gfx_get_info`
reports the shown page; `gfx_set_mode` shows page 0; a page other
than 0 or 1 is `-KOS_EINVAL`, and both new calls flush a pending
batch first.  No OS change: the v9958 driver and the kernel image
are untouched.

The peer model grew to match: with the frame clock on, status
register 2's VR follows the frame's last 50 of its 262 lines; R#2
writes record the displayed page; and with the duration model on,
each command keeps CE busy for its execution time, computed per byte
or dot from openMSX's VDPCmdEngine deltas (which reproduce the chip;
display on, sprites off) - HMMV 16 T-states per byte, HMMM 29.3 per
byte, LMMV 32 per dot, LINE 28 per dot, PSET one 40-T access, plus
40 T of issue overhead - converted to the peer's one-per-instruction
clock at the CE poll loop's rate (ten T-states an instruction).  The
model omits the display's access-slot contention: real commands run
about 20% longer.

## Checkpoints

1. **Asynchronous order.** `gfxtest pages` fills a rectangle,
   returns, and uploads a pattern over it: the replay finds a
   CE-busy status read between the fill's start and the upload's
   first VRAM address, and the upload's bytes win row by row.
2. **The batch returns with CE still set.** A 32-fill batch between
   two marks: the mark after `gfx_end` lands before the last fill's
   CE clears, and the replay prices the CPU's queue-and-return time
   (see Budgets).  The fills' blocks and every packed byte are
   pinned.
3. **CPU VRAM waits.** The upload, the text sink, the palette, the
   mode set, `gfx_close` and the page switch all wait for CE first;
   the whole gfxtest surface passes unchanged (the existing 21
   replays pin the upload, text and palette paths).
4. **The page switch.** Page 1's picture (a full clear plus a
   70-line band) is drawn, `gfx_show_page(1)` runs, and the replay
   checks the R#2 write's frame-clock position: inside the retrace
   window, value 0x3F, the shown page 1.
5. **Frame pacing.** Three `gfx_wait_vblank` calls in a row: the
   replay counts exactly three VR rising edges between the bracketing
   marks, one retrace per frame.
6. **Partial present.** Back to page 0 (R#2 = 0x1F inside the next
   retrace), one `gfx_wait_vblank`, then the 512x70 band copied from
   page 1: page 0's band equals page 1's byte for byte, the rest of
   page 0 is untouched, and the HMMM block carries the full width.
7. **Refusals and restore.** `gfx_show_page(2)` is `-KOS_EINVAL`;
   the release puts the console back (the hold sequence, the restored
   registers, palette and cursor tables, the exclusive flag clear).

## Budgets

| figure | now |
|---|---|
| one command, queue + flush (CPU, CE wait excluded) | 308 T-instructions (package 93's pin, unchanged) |
| a 32-command batch: CPU time to return, VDP still busy | 14,367 instructions |
| HMMM band copy, 512x64 G6, VDP time (duration model) | 480,637 T-states at 3.58 MHz = 134 ms |
| the vertical blank | 50/262 of a frame = 3.18 ms |

The 512x64 band copy is about 42 retraces: a partial present of that
size tears.  One 512-dot row costs 7,549 T-states (2.1 ms) and fits
inside the blank; two rows (15,059 T, 4.2 ms) just miss.  The owner
checklist notes the board's actual tear point.
